01 — System Architecture

The four-layer
agentic stack.

AEGIS is designed as a genuinely agentic, generative AI system — not a workflow tool with AI bolted on. Each layer has a distinct responsibility, a defined interface, and a regulatory justification. The stack is deployable end-to-end on Google Cloud Platform's always-free tier with zero marginal cost at portfolio traffic volumes.

L1
Presentation &
Experience
User Interface — Static Site + Functional App
The human-facing surface. Two deployments from one repository: the design documentation site (GitHub Pages, static HTML/CSS/JS) and the functional governance app (served from Cloud Run, same frontend codebase). The Documentation Lead interacts exclusively at this layer — submitting intakes, viewing classifications, tracking approvals, and generating audit packages. No technical knowledge required. No backend infrastructure visible to the user.

L2
Agent
Orchestration
Python FastAPI — Orchestrator + Five Specialist Agents
The intelligence layer. A master Orchestrator Agent receives every intake submission and delegates to five specialist agents: Intake, Classification, Oversight, Audit, and Explainability. Each agent is a structured Python function with a defined prompt template, a policy context injection, and a typed response schema. Agents operate sequentially in the happy path and branch on exceptions. Every agent call produces a plain-language explanation of its decision before returning its result — explainability is not a post-processing step, it is the first output of every agent.

L3

Intelligence
Gemini API + Policy-as-Context + Prompt Registry
The model layer. Google Gemini 2.0 Flash (via Google AI Studio free tier) provides the generative intelligence for all agent reasoning. The three governance policies — AI Content Working Standard, Human Oversight Documentation Standard, and Model Documentation Minimum Standards — are injected as system context into every agent prompt. This is policy-as-context: the policies are not hardcoded logic, they are the reasoning substrate. A dedicated prompt registry in the repository tracks prompt versions, so changes to prompts are auditable — the same standard AEGIS enforces on AI documentation is applied to itself.

05 — Agent Orchestration Design

Five specialist agents.
One governance outcome.

Each agent owns exactly one governance responsibility. No agent does more than one thing. This is not an architectural preference — it is an IAPP AIGP explainability requirement. A system where one agent does everything cannot explain what it did or why. Single-responsibility agents produce single-responsibility explanations.

Agent 01
⬡
Intake Agent
Receives the Documentation Lead's submission. Validates all mandatory fields against the Model Documentation Minimum Standards Policy. Blocks incomplete submissions before any downstream agent is called. Returns a structured payload or a field-level rejection with a plain-language explanation of what is missing and why it is required.
Enforces: Model Documentation Minimum Standards Policy §5 · EU AI Act Annex IV §1
Agent 02
◈
Classification Agent
Applies EU AI Act Annex III logic to classify the submitted AI system by risk tier: Prohibited, High-Risk, Limited-Risk, or Minimal-Risk. The classification is not hardcoded — it is reasoned by Gemini against the Annex III criteria injected as context. Every classification comes with a plain-language explanation: which criterion triggered the tier, and what compliance obligations follow from it.
Enforces: EU AI Act Articles 6–7, Annex III · NIST AI RMF GOVERN 1.4
Agent 03
◉
Oversight Agent
Determines the human oversight requirements for the artifact based on its risk tier and content type. Specifies who must review, what they must verify, and what constitutes a valid approval record. Generates the oversight record template and tracks reviewer identity once approval is submitted. A record that cannot be linked to a named, qualified reviewer is rejected.
Enforces: Human Oversight Documentation Standard · EU AI Act Article 14 · SR 11-7 §IV
Agent 04
▣
Audit Agent
Assembles the complete evidence chain for any AI artifact on demand: intake record, classification decision with rationale, oversight record with reviewer identity, version history, and policy citations. The output is an Annex IV-compliant technical documentation bundle — structured, timestamped, and ready to send to a regulator within minutes of request. This is the agent that answers the FCA's Section 165 notice.
Enforces: EU AI Act Annex IV · FCA SYSC · SR 11-7 Model Documentation
Agent 05
◎
Explainability Agent
Wraps every decision made by agents 01–04 in a plain-language explanation written for a non-technical audience. Not a post-processing step — this agent is called by every other agent before it returns its result. The explanation answers three questions: what did the system decide, why did it decide that, and what does the human need to do next. This is IAPP AIGP's explainability principle operationalised as code.
Enforces: IAPP AIGP Explainability Principle · EU AI Act Article 13 · NIST AI RMF GOVERN 6.2
06 — Architecture Decision Records

Five decisions.
All justified.

Architecture Decision Records document why the system is built the way it is — not just what was chosen, but what was considered and rejected, and the consequences of each decision. In a governance system, ADRs are themselves a governance artifact. Click any record to expand.

ADR-001
Cloud Run over App Engine or Cloud Functions
Backend compute host for the FastAPI agent orchestration layer
Accepted
+
Context
The AEGIS backend needs to host a Python FastAPI application that runs five agents per request. The application is a portfolio project with intermittent traffic. Infrastructure cost must be zero at current scale. The host must be deployable from a GCP free trial account.
Options considered
✓ Chosen — Cloud Run
Serverless containers. Scales to zero. 2M requests/month free. Supports any language or framework. Deploy a Docker container with a single gcloud command. No idle cost.
Rejected — App Engine
More opinionated runtime. Free tier is more restrictive for custom frameworks. Instance startup is slower. Less suited to containerised agentic workloads.
Rejected — Cloud Functions
Function-level granularity is too fine for an orchestration layer. Managing five functions separately adds deployment complexity with no architectural benefit at this scale.
Consequences
Positive: Zero idle cost. Full framework flexibility. Docker-based deployment is transferable to any enterprise container platform. Demonstrates production-grade containerisation skills. Negative: Cold start latency (~1s) on first request after idle period. Acceptable for a portfolio app; would require minimum instances in production.
ADR-002
FastAPI over Flask or Django for agent orchestration
Python web framework for the L2 backend
Accepted
+
Context
The backend needs to handle structured JSON payloads from the intake form, route them through multiple agents, and return typed, validated responses. Pydantic schema validation is a requirement because agent outputs must be predictable for downstream consumption.
Options considered
✓ Chosen — FastAPI
Native Pydantic integration. Automatic OpenAPI documentation generation. Async support for concurrent agent calls. Type hints are enforced at runtime. Standard in financial services Python backends.
Rejected — Flask
No native schema validation. Async support requires additional libraries. OpenAPI docs require manual configuration. Less appropriate for typed, agent-driven payloads.
Rejected — Django
Significant overhead for an API-only service. ORM and template engine are unnecessary. Boot time and footprint are too large for a Cloud Run container that scales to zero.
Consequences
Positive: Auto-generated /docs endpoint makes the API self-documenting — directly relevant for a governance system. Pydantic enforces the same typed schema discipline AEGIS requires of the AI artifacts it governs. FastAPI is the dominant framework in the enterprise Python AI/ML ecosystem. Negative: Slightly steeper learning curve than Flask for contributors unfamiliar with async Python.
ADR-003
Server-side Gemini API key over user-supplied key
API key management pattern for the intelligence layer
Accepted
+
Context
The functional app calls the Gemini API for agent reasoning. The API key must be managed in a way that is secure, cost-controlled, and frictionless for end users. Google AI Studio provides a free tier with rate limiting built in.
Options considered
✓ Chosen — Server-side key
Key stored in Cloud Run environment variable. Never exposed to browser. Users experience zero friction. Google AI Studio rate limiting provides natural cost governance. Free tier is sufficient at portfolio traffic volumes.
Rejected — User-supplied key
Increases user friction. Requires API key input UI. Inconsistent experience for users without a Google AI Studio account. Appropriate for demo/simulation mode only — not the functional app.
Rejected — Anthropic API
No free tier. Every agent invocation incurs cost to the developer. Not viable for a public-facing portfolio app. Gemini 2.0 Flash provides equivalent reasoning capability for governance classification tasks.
Consequences
Positive: Zero user friction. Zero ongoing API cost. Key never in browser — no client-side credential exposure risk. Rate limiting is handled by Google, not by custom middleware. Negative: Server-side key means any abuse of the endpoint is billed to the developer's quota. Mitigated by Cloud Run's natural request throttling and Google AI Studio's built-in rate limits.
ADR-004
Policy-as-Context over a vector database for document retrieval
How governance policies are made available to agents at reasoning time
Accepted
+
Context
Agents need access to the three governance policies to reason against. Options range from hardcoded rules to RAG with a vector database. The policies are short (each under 10 pages), stable (quarterly review cycle), and authoritative — every agent must reason against the full text, not a chunk.
Options considered
✓ Chosen — Policy-as-Context
Full policy text injected into the system prompt of every agent call. No retrieval latency. No chunk boundary errors. Policy is the reasoning substrate, not a retrieved reference. Gemini 2.0 Flash's 1M token context window makes this trivial.
Rejected — Vector DB (RAG)
Unnecessary complexity for documents this size. Chunk boundaries risk retrieving partial policy clauses. Adds infrastructure cost (Pinecone, Vertex AI Vector Search). Not appropriate when the full document fits in context.
Rejected — Hardcoded rules
Removes explainability. A hardcoded rule cannot explain itself in plain language. Breaks when policy changes. Defeats the purpose of a generative AI governance system.
Consequences
Positive: Policy changes take effect immediately on next deployment — no re-embedding, no index rebuild. The system is self-consistent: it governs AI documentation using the same policies it enforces. Explainability is natural — the agent can cite the exact policy clause it reasoned against. Negative: Slightly larger prompt payload per request. Negligible at this scale.
ADR-005
Firestore over Cloud SQL for the governance audit log
Persistence layer for audit records, model registry, and approval events
Accepted
+
Context
Audit records need to be written immediately after each governance event (intake, classification, approval, audit package generation), retrievable on demand within seconds, and immutable once written. The schema will evolve as new agent types are added.
Options considered
✓ Chosen — Firestore
NoSQL document model matches the variable structure of governance records. 50K reads/day free. Schema-flexible — new agent outputs can be added without migrations. Native GCP integration — no VPC connector needed from Cloud Run.
Rejected — Cloud SQL
Relational model is too rigid for evolving governance record schemas. Requires a VPC connector from Cloud Run (additional cost). No always-free tier — minimum instance cost even when idle.
Rejected — In-memory only
Cloud Run scales to zero — in-memory state is lost between requests. Audit logs that exist only in memory are not audit logs. Unacceptable for a system claiming regulatory compliance.
Consequences
Positive: Zero cost within free tier limits. Document model is naturally audit-friendly — each governance event is a discrete document with a timestamp. Schema evolves without database migrations. Negative: No complex joins or aggregation queries. Acceptable — governance queries are document lookups by artifact ID, not analytical joins.
